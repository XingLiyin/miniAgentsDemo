  当前上下文组织策略                                                                                                               
                                                                                                                                   
  Actor 上下文                                                                                                                     
   
  System prompt（静态，每轮不变）：                                                                                                
  soul_md  +  资源列表（tools/skills/agents）  +  skill_instructions

  Messages（动态，两条路径）：

  普通路径：
  [recent_messages 窗口，去掉最后一条 user 消息]
  ↓
  user: {blackboard_snippets（Task Background）}
        {task.title + description}
        {task.user_prompt}

  Resume 路径（memory 里有当前 task_id 的挂起记录）：
  [recent_messages 全量还原]
  ↓
  user: {Sub-task results: blackboard_snippets}
        "Sub-tasks have completed. Please review the results and continue."

  ---
  Observer 上下文

  System prompt：role_md + 可用 control tools

  Messages（保持「一条 system + 一条 user」，在 user message 内分段渲染）：
  user：
        Current task: title / description
        Sub-task results / No sub-tasks
        User requirements: session.user_prompt
        Prior progress：当前 task 前序轮次，按轮次分组渲染，明确区分
                        === Round N === / [Agent reply] / [Process report] / [User reply]
                        （assistant 摘要以 `# Process Report` 拆成 agent 回复与 process_report；
                         丢弃首条包装 user_prompt）
        Current turns：本轮执行 transcript（result.conversation_turns 展开为文本）
        [Session task list]（仅当存在可复核 sibling 时）

  关键点：始终只有一条 user message；前序轮次与本轮分别在 Prior progress / Current turns 两段渲染。
  Observer 只看「当前 task」的前序轮次（不含其它 task 的 memory），仍不直接消费 blackboard_snippets。

  ---
  历史记忆的组织

  消息以 messages.jsonl 追加存储，每轮任务结束写入两条：

  role=user      ← task.user_prompt
  role=assistant ← verdict.summary（Observer 的 task_result + next_step_hint）

  窗口截取（get_window(n)）直接作为 recent_messages 使用，不做额外处理。

  压缩触发（消息数超阈值 或 context_tokens ≥ 80% limit）：
  - CompactionStrategy 将旧消息压缩为摘要文本
  - 压缩摘要作为 {"role": "assistant", "content": "[Context so far]: ..."} 前置写入保留消息
  - 旧消息从 messages.jsonl 裁掉
  - 下轮 get_window() 自然读到：压缩摘要消息 + 近期消息，无需单独字段

  无 CompactionStrategy 时不压缩，窗口永远是最后 N 条原始消息。

  ---
  整体特征

  - Actor 看到：完整身份指令 + 历史消息窗口 + 当前任务 + 子任务结果（resume 时）
  - Observer 看到：评估准则 + 当前 task 的前序执行轮次（process_report）+ 本轮执行过程
  - 跨轮持久化：只有 verdict.summary（Observer 产出）落地为 memory，Actor 的中间过程不保留
  - 压缩透明：压缩摘要混入消息列表，对 prompt builder 无感知，无独立的 summary 注入点


Blackboard 发布、拉取、组织机制                                                                                                  
                                                                                                                                   
  存储结构                                                                                                                         
                                                                                                                                   
  /data/blackboard/{session_id}/{topic}/entries.jsonl                                                                              
                                                            
  追加写入，每条 BlackboardEntry 包含：id / session_id / topic / publisher_id / content / created_at

  游标为纯内存态：_cursors: dict[(agent_id, session_id, topic) → int]，进程重启后丢失。

  ---
  发布（publish）

  触发点只有一处，在 AgentLoop.run() 任务完成后（agent_loop.py:166-172）：

  ┌─────────┬───────────────────────────────────────────┐
  │  topic  │                  content                  │
  ├─────────┼───────────────────────────────────────────┤
  │ task.id │ task.result（任务最终结果，供父任务消费） │
  ├─────────┼───────────────────────────────────────────┤
  │ _root   │ Actor 每轮 llm_text                       │
  ├─────────┼───────────────────────────────────────────┤
  │ _root   │ Actor 每次 tool call 格式化记录           │
  └─────────┴───────────────────────────────────────────┘

  _root 的写入目前无人消费（Reasoner 侧对应代码已注释）。

  ---
  拉取（pull）

  触发点只有一处，在 Reasoner._fetch_base() 中：

  for child in task_svc.list_children(task.id, session.id):
      for entry in bb_svc.pull(session.id, child.id, agent.id):
          bb_snippets.append(entry.content)

  - 遍历当前任务的直接子任务，以 child.task_id 为 topic 拉取
  - 基于游标增量读取，每次 pull 后游标递增，不会重复消费
  - 结果汇入 bb_snippets → ReasoningContext.blackboard_snippets

  ---
  消费路径

  blackboard_snippets 进入 prompt 有两条路径：

  Resume 路径（Actor，prompt_builder.py:124）：
  user: "Sub-task results:\n- {snippet}\n..."
        "Sub-tasks have completed. Please review the results and continue."

  非 Resume 路径（Actor，prompt_builder.py:146）：
  user: "Task Background:\n- {snippet}\n..."
        ...当前任务描述...

  Observer 不消费 blackboard_snippets，通过 Actor 本轮 transcript 间接感知。

  ---
  整体特征

  - 拓扑：严格父→子单向，只有父任务能 pull 子任务结果，无横向（sibling）通信
  - 时序：子任务全部 terminal 后父任务 resume，父任务的下一轮 Reasoner 才能 pull 到结果
  - 幂等性：游标机制保证同一批结果不被重复注入，但游标不持久化
  - _root topic：有写无读，当前是死数据


Blackboard 内容组织结构                                                                                                          
                                                                                                                                   
  文件布局                                                                                                                         
                                                                                                                                   
  /data/blackboard/{session_id}/{topic}.jsonl                                                                                      
                                                                                                                                   
  每个 topic 一个文件，topic 直接作为文件名。当前实际产生的 topic：

  - {task.id} — 每个完成的子任务各一个文件，内容是该任务的 task.result
  - _root — 所有 Actor 的 llm_text 和 tool call 记录混写在一起（无人消费）

  每条 entry 结构：id / session_id / topic / publisher_id / content / created_at，追加写、不可变。

  ---
  Push 的特点

  触发时机：AgentLoop.run() 末尾，任务状态确认为 FINISHED 后同步写入（agent_loop.py:166-172）。

  写入内容分析：

  # 第一条：任务最终结果
  bb_svc.publish(session_id, task.id, agent_id, task.result)

  # 后续 N 条：Actor 每轮 llm_text + 每次 tool call 各一条
  for result_turn in result.conversation_turns:
      bb_svc.publish(session_id, "_root", ...)

  关键问题：task.id 这条只在 task.status == "FINISHED" 时写入（agent_loop.py:166），FAILED 或 SUSPENDED 的任务不写。_root
  的写入没有状态门控，每轮都写，无论任务最终结果如何。

  内容粒度：task.result 是单条聚合结果（Observer 产出的 task_result 字段），而 _root 是细粒度的原始流水，两种粒度混在不同 topic
  里，没有统一。

  ---
  Pull 的特点

  触发时机：Reasoner._fetch_base() 每次构建 ReasoningContext 时同步调用。

  游标机制：

  key = (agent_id, session_id, topic)
  cursor = self._cursors.get(key, 0)          # 默认从头读
  raw_entries = store.read_since(session_id, topic, cursor)
  self._cursors[key] = cursor + len(entries)  # 只在本次返回了内容时才推进

  read_since 实现是 read_all()[cursor:]，即每次 pull 全量读文件再切片，没有真正的增量 IO。

  增量语义的问题：游标是内存态，进程重启后归零。重启后父任务再次被调度时，同一批子任务结果会被重复 pull 并注入
  prompt。同一进程内如果父任务被多次 resume（理论上不应发生，但 PENDING 重试路径存在），第二次 pull
  返回空列表（游标已推进），子任务结果就消失了。

  拓扑约束：只 pull 直接子任务（list_children(task.id)），不递归，孙任务结果对祖父任务不可见，需要子任务自己在 task.result 里汇总。

# compact机制

---                                                                                                                              
  Compact 触发条件                                                                                                                 
                                                                                                                                   
  AgentLoop.run() 末尾，每轮任务结束后检查（agent_loop.py:175）：                                                                  
                                                                                                                                   
  if self._memory_svc.should_summarize(                                                                                            
      agent_id,                                             
      context_tokens=agent.loop_guard.context_tokens,
      context_limit=agent.loop_guard.context_limit,
  ):
      self._do_summarize(session_id, agent_id, verdict.summary)

  should_summarize() 满足任一条件即触发：
  - 自上次 compact 以来新增消息数 ≥ default_summary_threshold（默认 20）
  - 本轮 context_tokens（Actor LLM 最大 prompt_tokens）≥ context_limit × 80%（默认 180,000 × 80%）

  SUSPENDED 路径（任务挂起等待子任务）不触发——run() 在写完挂起记录后直接 return，不到检查点。

  ---
  Compact 执行过程

  _do_summarize(session_id, agent_id, latest_summary) 内：

  1. 拉取全量消息
  messages = self._memory_svc.get_window(agent_id, 10000)

  2. 调用 MemoryCompactionAgent
  kept, compacted_summary = self._compaction_agent.compact(
      messages=messages,
      session_goal=session.goal,
      working_dir=working_dir,
      session_id=session_id,
      agent_id=agent_id,
  )

  compact() 内部：
  - 消息数 > keep_last：正常切分，压缩旧的，保留新的
  - 消息数 ≤ keep_last：全部作为 to_compact，kept = []，LLM 对全部消息生成摘要，结果只剩 [Context so far] 一条消息
  - 切分：to_compact = messages[:-6]，kept = messages[-6:]
  - 起 LLM 多轮循环（最多 8 轮），soul 来自 resources/agents/memory-compactor/SOUL.md
  - LLM 可调用 read / glob（白名单来自 SOUL.md tools.required）查阅相关文件
  - 最后一轮纯文本输出 = compacted_summary
  - LLM 调用失败时静默回退，返回原始消息列表

  3. 失败降级
  消息截断为最后 keep_last 条，无摘要头，covered_up_to 和 context_tokens 正常更新。

  ---
  Compact 结束后的变化

  消息列表重写（有压缩产出时）：
  kept = [{"role": "assistant", "content": f"[Context so far]:\n{compacted_summary}"}] + kept
  self._memory_svc.rewrite_messages(agent_id, kept)
  - messages.jsonl 被原文件归档为 .bak.jsonl，重写为 [Context so far] 消息 + 最后 6 条消息
  - 下轮 get_window() 读到的是压缩后的短列表

  MemorySummary 更新：
  self._memory_svc.save_summary(agent_id, MemorySummary(
      summary_text=summary_text,
      covered_up_to=count,   # 压缩后的消息总数
      ...
  ))
  - covered_up_to 更新为当前消息数，用于下次 should_summarize() 的阈值计算

  context_tokens 清零：
  agent.loop_guard.context_tokens = 0
  消息被裁短后原有的 token 测量值失效，强制下轮重新测量。

# system prompt中引入项目背景内容

  核心思路                                                                                                                         
                                                                                                                                   
  项目背景（Project Background）是静态的、描述工作项目本身的上下文，与 agent soul（身份）、memory（历史）都不同。它应该：          
  - 存储在 agent 工作目录下，随项目走                                                                                              
  - 由 Reasoner 在构建上下文时读入                          
  - 通过 ReasoningContext 传给 PromptBuilder，注入 system prompt

  ---
  1. 文件约定

  {working_dir}/BACKGROUND.md

  - 位置：agent 的 settings.working_dir 目录下
  - 命名：固定为 BACKGROUND.md，用户手动维护
  - 格式：纯 Markdown，无需 frontmatter
  - 存在即读，不存在则跳过（background 为空不影响运行）

  ▎ 选 working_dir 而非全局 agents_dir：项目背景跟着项目走，不同 working_dir 对应不同项目背景，更自然。

  ---
  2. ReasoningContext 新增字段

  # app/runtime/types.py
  @dataclass
  class ReasoningContext:
      # ... 现有字段 ...
      project_background: str = ""   # 从 working_dir/BACKGROUND.md 读入

  ---
  3. Reasoner 加载逻辑

  在 Reasoner.reason() 中新增一个私有方法 _load_background(agent)，独立于 _fetch_base()（保持后者职责单一）：

  # app/runtime/reasoner.py

  def reason(self, session, agent, task):
      messages, bb_snippets, token_estimate = self._fetch_base(session, agent, task)
      soul, role, skill_instructions = self._extract_agent_identity(agent, task, session.id)
      project_background = self._load_background(agent)

      return ReasoningContext(
          ...
          project_background=project_background,
      )

  def _load_background(self, agent: Agent) -> str:
      working_dir = (agent.settings or {}).get("working_dir", "")
      if not working_dir:
          return ""
      bg_path = Path(working_dir) / "BACKGROUND.md"
      try:
          return bg_path.read_text(encoding="utf-8") if bg_path.is_file() else ""
      except Exception:
          logger.debug("Reasoner: failed to read BACKGROUND.md from %s", bg_path)
          return ""

  ---
  4. PromptBuilder 注入点

  ActorPromptBuilder 注入在 soul 之后、resources 之前：

  soul
  ───
  ## Project Background
  {content}
  ───
  ## Available Skills / Tools / Sub-Agents
  {resources}
  ───
  {skill_instructions}

  ObserverPromptBuilder 不注入：Observer 评估的是执行过程，不需要项目背景。

  具体改动：

  # ActorPromptBuilder.build_system_prompt()
  def build_system_prompt(self, ctx: "ReasoningContext") -> str:
      parts = [p for p in [
          ctx.soul,
          self._build_background_section(ctx),
          self._build_resources_section(ctx),
          ctx.skill_instructions,
      ] if p]
      return "\n\n---\n\n".join(parts)

  def _build_background_section(self, ctx: "ReasoningContext") -> str:
      if not ctx.project_background:
          return ""
      return f"## Project Background\n\n{ctx.project_background}"
