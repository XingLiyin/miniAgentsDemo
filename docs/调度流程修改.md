                                                                                     
  一、Session 启动                            
                                          
  API
    └─ SM.create_session                                                               
         ├─ session_svc.create()
         ├─ agent_store.save(root_agent)                                               
         ├─ LM.init_session()                               
         ├─ LM.register_root_agent()        写入 registry，parent_id=None
         └─ SM._create_initial_task()       task_svc.create(PENDING)

    └─ SM.schedule_loop(session_id, agent_id)
         └─ TM.start_session(session_id, agent_id)
              ├─ session_svc.transition(RUNNING)
              ├─ task_svc.list_pending()
              └─ TM._dispatch_next(session_id, agent_id, task)

  二、_dispatch_next（TM 唯一路由出口）

  TM._dispatch_next(session_id, finished_agent_id, next_task)

    next_task = None →
      LM.release(session_id, finished_agent_id)
        └─ _settle_executor → 回收 sub（如有），得到 executor
           _recycle(executor)
      return

    task_svc.transition(next_task.id, ACTIVE)

    agent_id = LM.prepare_executor(
        session_id, finished_agent_id, task_id,
        use_subagent, template_name, inherit_memory
    )
      └─ _settle_executor     回收 sub（如有），得到 base_executor
         use_subagent=False → 返回 base_executor
         use_subagent=True  →
             _check_spawn_permission
               通过  → _instantiate_sub_agent(parent_id=base_executor)
                       写入 registry(parent_id, spawn_depth=1)
                       返回 new_sub_agent_id
               拒绝  → 发 SPAWN_REJECTED，返回 base_executor（降级）

    LM.run_agent(session_id, agent_id, next_task.id)
      └─ 更新 registry.task_id
         daemon thread → LM._execute

  三、LM._execute

  LM._execute(session_id, agent_id, task_id)
    AgentLoop.run(session_id, agent_id, task_id)
    成功 → 发布 TASK_EXECUTION_FINISHED
    异常 → 发布 TASK_EXECUTION_FAILED

  四、Task 完成后续接

  TM.on_task_finished（TASK_EXECUTION_FINISHED）
    ├─ record_success
    ├─ [session lock]
    │    检查 session.status ∈ {RUNNING, QUEUED}
    │    _try_resume_parent(finished_task_id)
    │    task_svc.list_pending() → next_task / None
    │    无 pending → session_svc.transition(SUCCEEDED)
    └─ _dispatch_next(session_id, agent_id, next_task)

  TM.on_task_failed（TASK_EXECUTION_FAILED）
    ├─ record_failure
    ├─ [session lock]
    │    task_svc.fail(task_id)            ACTIVE → FAILED
    │    retry_count < max → task_svc.retry()，next_task = 同一 task
    │    超限且有 pending  → next_task = pending[0]
    │    超限且无 pending  → session_svc.transition(FAILED)
    └─ _dispatch_next(session_id, agent_id, next_task)

  ---
  职责边界

  SM   创建 Session / Agent / Task，通知 TM 启动
  TM   全部决策：session 状态、task 激活/失败/重试、resume 父任务、读 task 属性
  LM   agent tree 管理：注册、装配、回收；执行层起线程

  三条对外接口：
  - SM → TM.start_session
  - TM → LM.prepare_executor / release / run_agent
  - LM → EventBus(TASK_EXECUTION_FINISHED/FAILED)

  关键接口变化

  事件命名：AGENT_FINISHED/FAILED → TASK_EXECUTION_FINISHED/FAILED，语义从 agent 视角改为 task 视角

  TM → LM 接口（从散乱的多方法调用收敛为三个）：
  LM.prepare_executor(...)   装配执行 agent，返回 agent_id
  LM.release(...)            session 结束，清理 agent tree

  Bug 修复

  1. sub-agent 完成后父任务永不恢复：resume 逻辑原来只在 root agent 路径，移入 TM 后对所有完成路径统一执行

 Task Queue 改动总结                                                                                                                                
                                                                                                                                                     
  起点问题                                                                                                                                           
                                                                                                                                                     
  原来的 task_queue.py 是个空 stub，list_pending 直接在 TaskService 里做时间排序，完全忽略依赖关系。                                                 
                                                                                                                                                     
  ---
  一、引入有状态 Push Queue                                                                                                                          
                                                                                                                                                   
  数据结构：两区分离

  _ready:   list[str]   栈（LIFO）— deps 已满足，可立即执行
  _blocked: set[str]    集合      — dag_deps 未满足，等待中

  接口：

  ┌───────────────────────────────────────┬───────────────────────────────────────────────────────────┐
  │                 方法                  │                           语义                            │
  ├───────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ push(session_id, task_id)             │ deps 满足 → 入栈；不满足 → 入 blocked                     │
  ├───────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ pop(session_id) -> Task               │ 弹出栈顶（LIFO），跳过非 PENDING                          │
  ├───────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ notify_completed(session_id, task_id) │ 某 task 完成后，将 blocked 中 deps 现已满足的 task 移入栈 │
  ├───────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ is_empty / has_work                   │ 两区均空 → session 可结束；有任一非空 → 还有任务          │
  └───────────────────────────────────────┴───────────────────────────────────────────────────────────┘

  选用栈而非队列：子任务（如 submit_task 产生的）入栈顶，优先于其他任务执行，自然产生深度优先执行顺序。

  ---
  二、三个显式 Push 点（在 TM 里）

  ┌─────────────────────────┬─────────────────────────────────────┬──────┐
  │          时机           │                位置                 │ 操作 │
  ├─────────────────────────┼─────────────────────────────────────┼──────┤
  │ task 被创建             │ 订阅 TASK_CREATED → on_task_created │ push │
  ├─────────────────────────┼─────────────────────────────────────┼──────┤
  │ 父任务从 SUSPENDED 恢复 │ _try_resume_parent resume 之后      │ push │
  ├─────────────────────────┼─────────────────────────────────────┼──────┤
  │ 失败任务重试            │ on_task_failed retry 之后           │ push │
  └─────────────────────────┴─────────────────────────────────────┴──────┘

  ---
  三、TM 调度逻辑替换

  list_pending()[0] → pop()，not pending → is_empty()，新增 notify_completed 调用。

  on_task_finished 新增了 blocked 等待分支：pop()=None 但 has_work()=True 时，说明 deps 尚未满足，不标 SUCCEEDED，等后续 task 完成触发
  notify_completed 再升入栈。

  ---
  四、dag_deps 填充（submit_plan）

  TaskService.create 加 dag_deps 参数。

  _handle_submit_plan 创建任务时建链：

  A.dag_deps = []
  B.dag_deps = [A.id]
  C.dag_deps = [B.id]

  保证 A→B→C 顺序执行：B 在 push 时因 A 未完成进入 blocked，notify_completed(A) 后 B 升入栈，以此类推。

  同时挂起父任务（与 submit_task 对称），子任务全部完成后父任务恢复，LLM 评估结果后收尾。
